# soobak 문체 가이드

이 문서는 하드웨어 기초 1~4편과 그래픽스 수학 1~4편을 기준으로 정리한 soobak 글쓰기 기준이다. 앞으로 다른 글을 soobak 문체로 수정할 때 문장 표현뿐 아니라 문단 구조, 설명 순서, 기술적 거리감, 톤을 맞추는 기준으로 사용한다.

## 핵심 인상

soobak 글은 Unity 개발자가 이미 겪는 현상에서 출발해, 그 뒤에 있는 하드웨어나 수학 구조로 차분히 들어가는 설명문이다. 독자를 몰아붙이지 않고, 개념을 하나씩 놓은 뒤 앞뒤 관계를 연결한다. 문장은 격식 있는 `습니다`체를 유지하며, 과장이나 감정 표현 없이 기술적 원인과 실무적 의미를 설명한다.

글의 목적은 지식을 많이 나열하는 것이 아니라, 독자가 Unity 코드, 셰이더, 프로파일러 결과를 볼 때 어떤 기준으로 해석해야 하는지 세워 주는 데 있다.

## 전체 구조

1. 이전 글 또는 독자가 아는 Unity 경험에서 시작한다.
   - "이전 글에서는 ... 다루었습니다."
   - "Unity에서 ... API 호출로 끝나지만, 내부에서는 ..."
   - "프로파일러에서 ... 상황이 보인다고 해서 ..."

2. 이번 글의 문제의식을 먼저 좁힌다.
   - 왜 이 개념이 필요한지 설명한다.
   - 단순 정의보다 "어떤 상황에서 문제가 되는지"를 먼저 보여 준다.
   - 예: CPU-bound, 메모리 대기, 그래픽 부하, 깊이 정밀도, 좌표 변환.

3. 큰 개념에서 세부 개념으로 내려간다.
   - 구조 설명 → 용어 정의 → 동작 원리 → 예시 → Unity나 게임에서의 의미.
   - 하드웨어 글은 역사나 구조의 변화가 "이전 구조의 한계가 다음 구조로 이어짐"의 형태로 전개된다.
   - 그래픽스 수학 글은 수학식 자체보다 "이 값이 렌더링에서 어떤 역할을 하는지"를 중심으로 전개된다.

4. 섹션 사이에는 맥락을 연결하는 문단을 둔다.
   - "다만 ..."
   - "하지만 ..."
   - "이 지점부터는 ..."
   - "다음으로 ..."
   - "이 좌표가 ... 결과가 ..."

5. 마지막은 `## 마무리`로 정리한다.
   - "이번 글에서는 ... 살펴보았습니다."로 시작한다.
   - 핵심 내용을 5~7개 정도의 bullet로 압축한다.
   - 마지막 문단에서 다음 글로 이어지는 이유를 설명한다.
   - 관련 글과 전체 시리즈 목차를 붙인다.

## 문장 톤

- 기본 말투는 차분한 존댓말 설명체다.
  - "...입니다."
  - "...합니다."
  - "...됩니다."
  - "...할 수 있습니다."
  - "...로 볼 수 있습니다."
  - "...에 가깝습니다."

- 강한 단정은 피하고 기술적으로 안전한 표현을 쓴다.
  - "항상"보다 "보통", "많은 경우", "일반적인 경우".
  - "무조건 좋다"보다 "...에 유리합니다", "...할 수 있습니다".
  - "최고"보다 "효과적입니다", "중요합니다".

- 감정적 표현, 농담, 비유적 장식은 거의 쓰지 않는다.
  - 글은 담백하고 기능적이다.
  - 문체의 힘은 과장이 아니라 원인과 결과의 연결에서 나온다.

- 독자를 꾸짖거나 설득하려 하지 않는다.
  - "반드시 알아야 한다"보다 "알아야 원인을 좁힐 수 있습니다."
  - "이렇게 해야 합니다"보다 "이렇게 보는 편이 좋습니다."

## 자주 쓰는 연결어

- 대조: `다만`, `하지만`, `반대로`
- 인과: `그래서`, `따라서`, `이 때문에`, `그 결과`
- 정리: `즉`, `결국`, `정리하면`
- 예시: `예를 들어`, `대표적입니다`, `... 같은`
- 범위 조절: `보통`, `많은 경우`, `일반적인`, `실무에서는`, `대부분`
- 흐름 전환: `이때`, `여기서`, `이후`, `다음으로`, `이 지점부터는`

## 용어 처리

- 중요한 기술 용어는 첫 등장 때 굵게 표시하고, 영어 원어를 괄호로 붙인다.
  - `**명령어(instruction)**`
  - `**파이프라인 해저드(Pipeline Hazard)**`
  - `**통합 메모리 아키텍처(UMA, Unified Memory Architecture)**`
  - `**동차 좌표(Homogeneous Coordinates)**`

- 용어를 정의할 때는 바로 기능이나 역할을 설명한다.
  - "레지스터는 CPU 코어 내부에 있는 매우 작은 고속 저장 공간입니다."
  - "내적은 이런 방향 관계를 숫자 하나로 바꾸는 연산입니다."

- 한국어 용어와 영어 용어의 균형을 맞춘다.
  - 본문에서는 한국어 중심으로 설명하되, API나 업계 용어는 원어를 유지한다.
  - `Vector3`, `Transform`, `fieldOfView`, `Dispatch()`, `SV_POSITION`처럼 코드상의 이름은 backtick으로 감싼다.

## 설명 방식

- 정의만 던지지 않고 "왜 필요한지"를 먼저 놓는다.
  - "명령어를 실행하려면 연산할 데이터도 필요합니다."
  - "3D 장면을 2D 화면에 그린다는 것은..."
  - "게임에서는 두 방향이 얼마나 비슷한지 판단해야 할 때가 많습니다."

- 원리 설명은 작은 단계로 나눈다.
  - 하나의 문단에 개념을 너무 많이 밀어 넣지 않는다.
  - 각 문단은 보통 하나의 논점만 갖는다.
  - 새 개념이 나오면 이전 개념과의 차이를 먼저 잡아 준다.

- 예시는 Unity나 게임 개발 상황에서 가져온다.
  - 캐릭터 이동, 적 AI, 오브젝트 상태 검사, 파티클, 조명, 카메라, 렌더 타깃, 모바일 발열.
  - 추상 개념을 설명한 뒤 "게임에서는", "Unity에서는"으로 다시 연결한다.

- 성능 설명은 측정과 조건을 함께 말한다.
  - 프로파일러, 반복문, 핫 루프, 모바일 지속 성능, GPU 계열 차이 같은 현실 조건을 함께 둔다.
  - "항상 빠르다"가 아니라 "이런 접근 패턴에서는 유리하다"로 쓴다.

## 문단 구조

좋은 soobak 문단은 다음 중 하나의 역할을 가진다.

- 문제 제기
  - 현재 방식으로는 왜 부족한지 설명한다.
  - 예: CPU가 데이터를 기다림, 고정 기능 GPU의 한계, 원거리 깊이 정밀도 부족.

- 정의
  - 용어를 짧게 정의하고, 바로 사용 맥락을 붙인다.

- 동작 원리
  - 입력이 어떤 단계를 거쳐 결과가 되는지 설명한다.

- 비교
  - A와 B의 차이를 구조, 장점, 한계로 나눠 설명한다.
  - 순차 접근 vs 랜덤 접근, 원근 투영 vs 직교 투영, AoS vs SoA, 데스크톱 vs 모바일.

- 실무적 의미
  - Unity 코드, 셰이더, 카메라 설정, 프로파일링에서 어떤 판단으로 이어지는지 설명한다.

- 다음 내용으로 넘기는 다리
  - "다만 ..."으로 남은 한계를 말하고, 다음 섹션이나 다음 글로 이어진다.

## 수식과 코드

- 수식은 설명을 대체하지 않는다. 수식 앞뒤에 의미를 풀어 주는 문장이 있어야 한다.
  - "이 식 때문에 ..."
  - "중요한 부분은 ..."
  - "수식으로 쓰면 ..."

- 수식의 각 기호는 본문에서 설명한다.
  - `n`, `f`, `d`, `w`, `x`, `y`, `z`처럼 축약된 값은 바로 뜻을 붙인다.

- 코드 예시는 짧고 역할이 명확해야 한다.
  - C#, HLSL, pseudo instruction을 보여 준 뒤 그 코드에서 어떤 값이 기다리거나 변환되는지 설명한다.
  - 코드 자체보다 코드가 드러내는 구조를 설명한다.

## 도식과 표

- 도식은 개념의 흐름을 보여 주는 용도다.
  - 파이프라인 단계, 메모리 계층, 좌표 공간 흐름, GPU 발전 흐름처럼 단계가 있는 내용을 시각화한다.

- 표는 비교를 압축할 때 쓴다.
  - 데스크톱 vs 모바일, 렌더링 셰이더 vs Compute Shader, Camera 속성처럼 항목별 차이가 분명한 경우에 사용한다.

- 도식 뒤에는 반드시 문장으로 다시 해석한다.
  - 독자가 그림을 보지 않아도 본문만으로 이해할 수 있어야 한다.

## 피해야 할 표현

- 과장된 홍보 문구
  - "압도적으로", "혁신적인", "놀라운", "강력한" 같은 표현은 피한다.

- 감상문식 표현
  - "흥미롭다", "재미있다"보다 구체적인 원인과 의미를 쓴다.

- 단정적인 최적화 조언
  - "항상 SoA가 좋다"처럼 쓰지 않는다.
  - "특정 필드만 대량으로 처리하는 루프에서는 SoA가 캐시 라인을 더 효율적으로 사용할 수 있습니다. 단, 항상 SoA가 더 좋은 것은 아닙니다."처럼 조건을 붙인다.

- 독자를 향한 직접 명령
  - "반드시 이렇게 하세요"보다 "이렇게 보는 편이 좋습니다", "확인해야 합니다" 정도로 쓴다.

## 수정할 때의 우선순위

1. 글의 출발점을 Unity나 게임 개발 맥락으로 맞춘다.
2. 정의보다 문제와 필요성을 먼저 세운다.
3. 용어는 한국어 설명과 영어 원어를 함께 정리한다.
4. 긴 문단은 문제, 원리, 의미 단위로 나눈다.
5. 수식과 코드는 주변 설명으로 의미를 보강한다.
6. 최적화나 성능 조언은 조건을 붙여 보수적으로 쓴다.
7. 마지막에는 핵심 요약과 다음 주제로 이어지는 문단을 둔다.

## 문체 변환 체크리스트

- 글이 `습니다`체로 통일되어 있는가.
- 각 섹션의 첫 문단이 그 섹션의 필요성을 설명하는가.
- 새 용어가 굵게 표시되고 영어 원어가 필요한 만큼 붙어 있는가.
- Unity API, 셰이더 코드, 프로파일링 상황으로 다시 연결되는가.
- "다만", "반대로", "따라서", "결국" 같은 연결어로 논리 흐름이 보이는가.
- 강한 단정 대신 조건과 범위를 제시했는가.
- 마무리에서 글 전체의 핵심과 다음 글의 맥락을 정리했는가.
