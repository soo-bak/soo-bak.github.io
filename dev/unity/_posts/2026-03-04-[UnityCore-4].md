## 프레임을 나누어 처리하는 스레드들

[Unity 엔진 핵심 (3) - Unity 실행 순서](/dev/unity/UnityCore-3/)에서는 `FixedUpdate`, `Update`, `LateUpdate`와 렌더링 콜백이 한 프레임 안에서 어떤 순서로 호출되는지 살펴보았습니다. 각 콜백이 **언제** 호출되는지는 이 실행 순서로 설명할 수 있습니다.

다만 실행 순서만으로는 각 콜백이 **어디에서** 실행되는지까지 알기 어렵습니다. Unity는 한 프레임을 하나의 스레드로 처리하지 않고 여러 스레드에 나누어 처리하기 때문입니다. 게임 로직을 실행하는 **메인 스레드(Main Thread)**, GPU에 렌더링 명령을 제출하는 **렌더 스레드(Render Thread)**, 병렬 연산을 처리하는 **워커 스레드(Worker Thread)**가 한 프레임의 작업을 나누어 맡습니다.

이 글에서는 먼저 메인 스레드와 렌더 스레드가 각각 무엇을 담당하는지, 두 스레드가 어디에서 서로를 기다리며 동기화되는지 정리합니다. 그다음 워커 스레드를 활용하는 Job System, Job 코드를 더 빠른 네이티브 코드로 바꾸는 Burst 컴파일러, Job이 다루는 데이터 컨테이너인 NativeContainer를 차례로 살펴봅니다. 이 구조를 알아 두면 Profiler(Unity 에디터의 성능 분석 도구)에서 어느 스레드가 어디서 기다리는지 읽어 내고, 어떤 작업을 워커 스레드로 넘겨 병렬화할 수 있는지 판단하는 데 도움이 됩니다.

## 메인 스레드

메인 스레드는 Unity 런타임의 중심 스레드입니다. 게임 상태를 갱신하고, 대부분의 Unity API 접근을 처리하며, 한 프레임에서 다른 시스템들이 사용할 데이터를 준비합니다.

### 모든 게임 로직의 실행 장소

게임 로직은 기본적으로 메인 스레드에서 실행됩니다. `Awake`, `Start`, `Update`, `FixedUpdate`, `LateUpdate` 같은 콜백뿐 아니라 충돌 콜백과 코루틴도 메인 스레드에서 실행됩니다. 일반적인 `MonoBehaviour` 스크립트 코드는 메인 스레드에서 호출된다고 보면 됩니다.

물리 시뮬레이션은 메인 스레드가 맡는 작업이지만, 그 연산까지 메인 스레드가 전부 처리하지는 않습니다. Unity가 쓰는 PhysX SDK는 멀티스레드를 지원하므로, 충돌 판정에 드는 무거운 계산은 여러 워커 스레드에 나누어 처리합니다. 다만 시뮬레이션을 시작하는 일, 워커 스레드의 계산이 끝나기를 기다려 그 결과를 받아 모으는 일, `OnCollisionEnter` 같은 충돌 콜백을 호출하는 일 등은 여전히 메인 스레드가 맡습니다.

무거운 계산을 이렇게 워커 스레드로 넘기는 이유는, 메인 스레드에 주어진 시간이 한정되어 있기 때문입니다. 물리뿐 아니라 메인 스레드가 처리하는 모든 작업은 한 프레임에 허용된 시간, 곧 **프레임 예산(frame budget)** 안에 끝나야 합니다. 예를 들어 화면을 60fps로 갱신한다면 한 프레임에 쓸 수 있는 시간은 약 16.6ms(1000ms / 60)에 불과합니다. 메인 스레드의 작업이 이 예산을 넘기면 프레임이 제때 끝나지 못하고, 화면이 끊기는 **프레임 드롭(frame drop)**으로 이어집니다. 충돌 판정처럼 비용이 큰 계산을 워커 스레드에서 처리하면, 그만큼 메인 스레드의 프레임 시간에 여유가 생깁니다.

> 프레임 예산과 프레임 드롭의 관계는 [게임 루프의 원리 (1) - 프레임의 구조](/dev/unity/GameLoop-1/)에서 자세히 다룹니다.

<br>

워커 스레드로 넘어가는 이 계산은, 결국 두 물체가 실제로 겹치는지 확인하는 일입니다. 장면에 물체가 늘어날수록 확인해야 할 물체 쌍이 빠르게 많아지고, 검사 비용도 그만큼 커집니다. PhysX는 이 검사를 두 단계로 나누어, 정밀한 판정을 꼭 필요한 쌍에만 집중시킵니다.

먼저 브로드페이즈(Broadphase)는 각 Collider의 AABB(Axis-Aligned Bounding Box, 축 정렬 경계 상자)만 비교해, 서로 닿을 가능성이 없는 쌍을 미리 걸러 냅니다. 실제 형상까지 들여다보지 않으므로 비용이 적습니다. 그다음 내로우페이즈(Narrowphase)는 이렇게 추려진 쌍만을 대상으로 실제 Collider 형상을 따져 충돌 여부를 정밀하게 판정합니다. 비용이 큰 계산은 이 내로우페이즈에 몰립니다.

워커 스레드가 나눠 맡는 것이 바로 이 내로우페이즈의 판정입니다. 한 쌍을 판정하는 계산은 다른 쌍의 판정과 얽혀 있지 않아, 어떤 쌍을 먼저 확인하든 결과가 달라지지 않습니다. 이렇게 쌍마다 독립적이므로, PhysX는 수많은 쌍의 판정을 여러 워커 스레드에 나누어 동시에 처리합니다.

<br>

### Unity API의 메인 스레드 제약

게임 로직이 메인 스레드에 집중되는 또 다른 이유는 Unity API의 대부분이 **메인 스레드에서만 호출할 수 있도록** 설계되어 있기 때문입니다.

<br>

| API | 스레드 제약 |
|-----|------------|
| `transform.position` | 메인 스레드만 가능 |
| `transform.rotation` | 메인 스레드만 가능 |
| `gameObject.SetActive()` | 메인 스레드만 가능 |
| `GetComponent<T>()` | 메인 스레드만 가능 |
| `Instantiate()` | 메인 스레드만 가능 |
| `Destroy()` | 메인 스레드만 가능 |
| `Resources.Load()` | 메인 스레드만 가능 |

<br>

이렇게 호출 스레드가 제한되는 이유는, 이 API들이 다루는 네이티브 엔진 객체가 여러 스레드의 동시 접근을 염두에 두고 만들어지지 않았기 때문입니다. 백그라운드 스레드에서 이런 객체에 접근하면, Unity가 잘못된 호출을 미리 막아 예외를 던지기도 하고, 아무 경고 없이 예측하기 어려운 동작으로 이어지기도 합니다.

이 가운데 예외는 호출할 때 바로 발생하므로 원인을 찾기 쉽습니다. 더 까다로운 쪽은 예측하기 어려운 동작입니다. 여러 스레드가 네이티브 C++ 객체의 상태를 동시에 수정하면 데이터 경합(Data Race, 여러 스레드가 같은 메모리에 동시에 접근하고 그중 하나 이상이 쓰기인 상황)이 일어나고, 그 결과는 곧바로 크래시로 이어지기도, 한참 뒤에야 데이터 손상으로 나타나기도 합니다.

이 규칙에서 벗어나는 경우가 하나 있습니다. `Debug.Log()`는 백그라운드 스레드에서 호출해도 대체로 안전합니다. Unity의 로그 시스템이 내부적으로 자체 동기화를 거치기 때문이며, 이 덕분에 백그라운드 작업을 디버깅할 때 자주 쓰입니다. 다만 이는 로그 시스템에 한정된 경우일 뿐, 다른 Unity API까지 같은 안전성이 보장되지는 않습니다.

따라서 무거운 계산을 백그라운드 스레드나 Job으로 넘기더라도, 그 결과를 Unity 오브젝트에 반영하는 단계는 메인 스레드에서 처리해야 합니다.

## 렌더 스레드

렌더 스레드는 메인 스레드가 준비한 렌더링 데이터를 GPU 명령으로 바꾸어 제출하는 스레드입니다. 화면에 무엇을 그릴지 정하는 일과 그 내용을 GPU에 그리도록 명령하는 일은 성격이 다르므로, Unity는 이 둘을 서로 다른 스레드에 나누어 맡깁니다.

### GPU 명령 제출 담당

렌더링이라고 해서 메인 스레드가 GPU에 명령을 보내는 일까지 도맡는 것은 아닙니다. 메인 스레드가 책임지는 범위는 무엇을 그릴지 정하고 그 데이터를 준비하는 데까지입니다. 화면에 보일 물체만 추려 내는 컬링, 그리는 순서를 정하는 정렬, 드로우 콜 목록 생성, 셰이더 파라미터 설정이 모두 이 단계에 해당합니다. 이렇게 준비된 데이터를 OpenGL이나 Vulkan 같은 그래픽 API 호출로 바꾸어 GPU에 제출하는 일부터는 렌더 스레드가 이어받습니다.

두 스레드는 내부 **명령 큐(Command Queue)**를 통해 연결됩니다. 메인 스레드가 렌더링 준비를 마치면 그 명령이 큐에 쌓이고, 렌더 스레드는 큐에서 명령을 하나씩 꺼내 GPU에 제출합니다. 이 명령 큐는 엔진이 내부에서만 쓰는 메커니즘으로, 스크립트에서 직접 다루는 것은 아닙니다.

### 프레임을 겹쳐 처리하는 파이프라이닝

메인 스레드와 렌더 스레드를 따로 둔 덕분에, 두 스레드는 동시에 일할 수 있습니다. 메인 스레드는 한 프레임의 렌더링 준비를 마쳐 명령을 큐에 넘기고 나면, 그 명령이 GPU에 제출되기를 기다리지 않고 곧바로 다음 프레임 작업에 들어갑니다. 그래서 메인 스레드가 다음 프레임의 게임 로직과 렌더링 준비를 이어 가는 동안, 렌더 스레드는 앞선 프레임의 명령을 GPU에 제출합니다. 두 프레임의 작업이 시간 위에서 한 칸씩 어긋난 채 나란히 진행되는 것입니다. 이렇게 작업을 여러 단계로 나누어 각 단계가 쉬지 않고 일하도록 맞물리는 방식을 파이프라이닝(pipelining)이라고 합니다.

파이프라이닝은 한 프레임을 더 빨리 끝내는 방법이 아니라, 같은 시간에 더 많은 프레임을 처리하는 방법입니다. 한 프레임이 온전히 끝나기를 기다렸다 다음을 시작할 때보다, 두 프레임을 겹쳐 처리하면 단위 시간에 완성하는 프레임 수, 곧 처리량(Throughput)이 늘어납니다. 

다만 한 프레임이 화면에 나오기까지 걸리는 시간은 오히려 늘어날 수 있습니다. 어떤 프레임이든 메인 스레드의 준비를 거친 뒤에야 렌더 스레드가 GPU에 제출하므로, 준비와 제출이라는 두 단계를 차례로 지나야 화면에 나타나기 때문입니다.
그만큼 입력이 화면에 반영되기까지의 지연(Latency)은 한 프레임만큼 늘어날 수 있습니다. 메인 스레드와 렌더 스레드뿐 아니라 CPU와 GPU 사이에서도 같은 원리의 파이프라이닝이 작동합니다.

> CPU/GPU 파이프라이닝은 [게임 루프의 원리 (1) - 프레임의 구조](/dev/unity/GameLoop-1/)에서 자세히 다룹니다.

## 메인 스레드와 렌더 스레드의 동기화

메인 스레드와 렌더 스레드가 파이프라인으로 맞물려 있는 한, 전체 프레임 속도는 둘 가운데 더 느린 쪽이 정합니다. 빠른 쪽은 느린 쪽이 일을 넘겨주거나 받아 갈 때까지 기다려야 할 뿐, 혼자 앞서 나아가지는 못하기 때문입니다. 따라서 이 절에서는 두 스레드가 어디에서 서로를 기다리는지 살펴보고, 그 기다림을 통해 게임의 병목이 어느 쪽에 있는지 읽어 내는 방법을 정리합니다.

### 동기화 대기 지점

메인 스레드가 준비한 렌더링 데이터를 렌더 스레드가 넘겨받는 지점은 프레임마다 정해져 있습니다. 두 스레드의 속도가 어긋나면, 이 지점에 먼저 도착한 쪽이 상대가 따라올 때까지 멈춰 기다립니다. 이렇게 두 스레드가 정해진 지점에서 서로 진행을 맞추는 과정을 **동기화(Synchronization)**라고 합니다.

둘 중 더 느린 스레드가 어느 쪽이냐에 따라, 기다리는 쪽이 정해집니다. 렌더 스레드가 GPU에 넘긴 작업을 GPU가 처리하는 데 오래 걸리면, 렌더 스레드는 그 완료를 기다리고 다음 프레임 준비를 마친 메인 스레드도 렌더 스레드를 기다립니다. 이렇게 GPU의 처리가 전체 속도를 제한하는 상태를 **GPU 바운드(GPU-bound)**라고 합니다. 반대로 메인 스레드가 게임 로직과 렌더링 준비에 오래 걸리면, 명령 제출을 마친 렌더 스레드가 다음 명령이 올 때까지 메인 스레드를 기다립니다. 이렇게 CPU, 곧 메인 스레드 쪽 처리가 전체 속도를 제한하는 상태가 **CPU 바운드(CPU-bound)**입니다.

### Profiler에서의 동기화 마커

앞서 본 두 상황은 Unity Profiler에 그대로 드러납니다. 스레드가 무엇을 기다렸는지에 따라 기록되는 마커(marker)가 달라지므로, 어떤 마커가 길게 잡히는지를 보면 병목이 어느 쪽에 있는지 좁힐 수 있습니다.

<br>

| 마커 이름 | 의미 |
|----------|------|
| `Gfx.WaitForPresentOnGfxThread` | 메인 스레드가 다음 프레임을 시작하려 하지만, 렌더 스레드가 GPU의 프레임 표시(present) 완료를 아직 기다리는 중 (GPU-bound 또는 VSync 대기) |
| `Gfx.WaitForCommands` | 렌더 스레드가 메인 스레드의 렌더링 명령을 기다리는 중 (메인 스레드 병목 가능성) |
| `Gfx.WaitForRenderThread` | 메인 스레드가 렌더 스레드의 명령 스트림 처리 완료를 대기 (멀티스레드 렌더링에서만 발생, 렌더 스레드 또는 GPU 병목) |

<br>

`Gfx.WaitForPresentOnGfxThread`가 길게 잡힌다면, 메인 스레드가 다음 프레임을 시작하려다 렌더 스레드와 GPU 쪽 처리가 끝나기를 기다렸다는 뜻입니다. 대체로 앞서 본 GPU 바운드를 가리키며, 병목은 GPU 작업이나 렌더 스레드 작업에 있을 수 있습니다.

다만 이 마커는 VSync(수직 동기화)가 켜져 있을 때도 길게 잡힐 수 있어, 해석에 주의가 필요합니다. VSync는 GPU가 디스플레이의 갱신 주기에 맞추어 프레임을 출력하도록 강제하는 기능으로, 프레임 처리가 갱신 주기보다 빨리 끝나면 다음 갱신 시점까지 기다립니다. 이 대기 시간도 `Gfx.WaitForPresentOnGfxThread`로 기록되므로, 마커가 길다고 해서 곧바로 GPU 병목이라고 단정할 수는 없습니다. 둘을 구분하려면 Profiler의 Timeline 뷰를 확인하면 됩니다. 이 마커 안에 `WaitForTargetFPS` 서브 샘플이 들어 있다면 VSync 대기이고, 렌더 스레드가 `Gfx.PresentFrame`에 시간을 쓰고 있다면 실제 GPU 병목입니다.

반대로 `Gfx.WaitForCommands`가 길다면, 렌더 스레드가 메인 스레드에서 렌더링 명령이 오기를 기다렸다는 뜻입니다. 명령을 준비하는 메인 스레드가 제때 따라오지 못한 CPU 바운드 신호이므로, 메인 스레드 쪽 부하를 살펴봐야 합니다.

<br>

## Job System

Job System은 메인 스레드에 몰린 계산 작업을 워커 스레드로 나누어 실행하기 위한 Unity의 병렬 처리 구조입니다. Unity API 접근은 제한되지만, 독립적인 데이터 계산을 분리하면 메인 스레드 부담을 줄일 수 있습니다.

### 멀티스레드 프로그래밍의 필요성

앞에서 본 구조는 게임의 CPU 작업을 주로 메인 스레드와 렌더 스레드로 나눕니다. 하지만 현대 CPU는 여러 코어를 가지므로, 동시에 실행할 작업이 두 개뿐이라면 나머지 코어는 충분히 활용되지 못합니다. CPU 바운드 구간에서 프레임 시간이 길어져도, 병렬로 나눌 작업이 없다면 비어 있는 코어를 활용할 수 없습니다.

Unity의 **Job System**은 이런 위험을 줄이면서 멀티스레드 작업을 예약하고 실행할 수 있도록 만든 프레임워크입니다.

### Job의 기본 구조

Job System은 작업을 Job이라는 단위로 만들고, 이를 여러 **워커 스레드(Worker Thread)**에 예약해 실행합니다. 메인 스레드가 Job을 스케줄링하면, 대기 중인 워커 스레드가 Job을 가져가 실제 연산을 수행합니다.

이 워커 스레드들은 Unity가 애플리케이션 시작 시점에 스레드 풀(pool)로 미리 만들어 둡니다. 개수는 CPU 코어 수, 플랫폼, Unity 설정에 따라 달라지며 보통 전체 코어 수보다 적습니다. 실제 워커 스레드 수는 `JobsUtility.JobWorkerCount`로 확인할 수 있습니다.

### IJob: 단일 작업

기본 형태는 `IJob`입니다. `IJob`은 작업 하나를 하나의 Job으로 예약하고, 워커 스레드가 이를 실행합니다. `struct`에 `IJob` 인터페이스를 구현하고, 워커 스레드에서 실행할 코드는 `Execute` 메서드에 작성합니다.

<br>

```csharp
// IJob 사용 예시

struct CalculatePathJob : IJob
{
    public Vector3 start;
    public Vector3 end;
    public NativeArray<Vector3> result;

    public void Execute()
    {
        // 경로 계산 로직 (워커 스레드에서 실행)
        // Unity API 호출 불가
        // result에 계산 결과 저장
    }
}

// 메인 스레드에서:
var job = new CalculatePathJob { ... };
JobHandle handle = job.Schedule();    // 워커 스레드에 예약
handle.Complete();                     // 완료 대기
// result 사용
```

<br>

`Schedule()`은 Job을 워커 스레드에 예약하고 곧바로 `JobHandle`을 반환합니다. 이 시점에는 예약만 된 것이므로, 메인 스레드는 Job이 실행되는 동안 다른 작업을 계속할 수 있습니다.
결과가 필요한 시점에 `JobHandle.Complete()`를 호출하면, 메인 스레드는 해당 Job이 끝날 때까지 기다린 뒤 결과를 사용할 수 있습니다.

<br>

### IJobParallelFor: 데이터 병렬

전체 모양은 `IJob`과 거의 같습니다. 다만 `Execute`가 `int index` 매개변수를 받아, 한 번 호출될 때 배열의 한 요소만 책임지도록 바뀝니다.

```csharp
// IJobParallelFor 구조

struct UpdateEnemiesJob : IJobParallelFor
{
    public NativeArray<Vector3> positions;
    public NativeArray<Vector3> velocities;
    public float deltaTime;

    public void Execute(int index)
    {
        // index번째 요소만 처리
        positions[index] += velocities[index] * deltaTime;
    }
}

// 메인 스레드에서:
var job = new UpdateEnemiesJob { ... };
JobHandle handle = job.Schedule(
    positions.Length,   // 총 작업 수
    64                  // 배치 크기 (워크 스틸링 단위, 한 번에 가져가는 요소 수)
);
handle.Complete();
```

<br>

`Execute`로 전달되는 `index`는 이 호출이 처리해야 할 배열 요소의 인덱스입니다. 워커마다 서로 다른 인덱스 범위를 처리하므로, 두 워커가 같은 요소를 동시에 수정하는 상황을 피할 수 있습니다.
직접 스레딩에서라면 락(Lock)으로 막아야 할 데이터 경합을, Job System은 작업 분할과 접근 규칙을 통해 줄입니다.

<br>

`Schedule`의 두 번째 인자인 배치 크기(`innerloopBatchCount`)는 인덱스를 몇 개씩 묶어 하나의 작업 덩어리로 다룰지 정합니다. Job System은 전체 인덱스를 이 크기로 나누어 워커들에게 배분합니다.
이 배치 단위는 워크 스틸링(Work Stealing)의 단위이기도 합니다. 먼저 작업을 끝낸 워커가 아직 작업이 남은 다른 워커의 배치를 가져와 처리하는 방식입니다. 배치가 너무 크면 일부 워커에 작업이 몰릴 수 있고, 너무 작으면 배치를 나누고 전달하는 관리 비용이 커집니다. 벡터 덧셈처럼 가벼운 연산에는 32~128, 호출 하나가 무거운 작업에는 1~16 정도가 흔히 사용됩니다.

<br>

최신 Unity에서는 `IJobFor`와 `ScheduleParallel()`도 사용할 수 있습니다. `IJobFor`는 같은 Job 코드를 두고 실행 방식만 선택할 수 있습니다. 메인 스레드에서 즉시 실행하려면 `Run()`, 단일 Job으로 예약하려면 `Schedule()`, 여러 워커에 나누어 실행하려면 `ScheduleParallel()`을 사용합니다.

## Burst 컴파일러

Burst 컴파일러는 Job 코드처럼 데이터 중심 계산에 특화된 코드를 더 빠른 네이티브 코드로 바꾸는 도구입니다. 단순히 C# 코드를 기계어로 옮기는 데서 끝나지 않고, SIMD 벡터화와 저수준 최적화를 함께 적용합니다.

### IL에서 최적화된 네이티브 코드로

앞에서 본 Job System은 작업을 여러 워커 스레드에 나누어 병렬로 실행합니다. 하지만 각 Job이 실행하는 코드 자체가 느리다면 병렬화만으로 얻는 이득에는 한계가 있습니다. **Burst 컴파일러**는 Job 코드 자체를 더 빠르게 실행되도록 컴파일하는 역할을 합니다.

Burst는 Job System과 짝지어 쓰는 고성능 컴파일러로, C# 컴파일러가 만들어 둔 IL(Intermediate Language, 중간 언어)을 입력으로 받습니다. 이 IL을 LLVM(여러 플랫폼에 맞는 최적화된 기계어를 만들어 주는 컴파일러 프레임워크)에 넘겨, 해당 플랫폼에 맞춘 네이티브 기계어로 변환합니다.

Burst가 성능을 높이는 대표적인 방법은 **SIMD(Single Instruction, Multiple Data) 자동 벡터화**입니다. SIMD는 CPU 명령어 하나로 여러 데이터를 한꺼번에 처리하는 하드웨어 기능입니다. 예를 들어 float 4개의 덧셈을 명령어 4번으로 처리하는 대신, SIMD 명령어 1번으로 처리할 수 있습니다(128비트 레지스터, 32비트 float 기준).

Job System과 SIMD는 서로 다른 수준의 병렬성입니다. Job System은 작업을 여러 코어에 나누는 스레드 수준 병렬성이고, SIMD는 한 코어 안에서 명령어 하나가 여러 데이터를 처리하는 데이터 수준 병렬성입니다. Burst는 코드를 분석해 가능한 경우 SIMD 명령어를 자동으로 생성합니다.

### [BurstCompile] 어트리뷰트

Burst를 켜는 방법은 단순합니다. Job 구조체에 `[BurstCompile]` 어트리뷰트만 붙이면, 해당 Job이 Burst로 컴파일되는 대상에 들어갑니다.

<br>

```csharp
// Burst 적용

[BurstCompile]
struct UpdatePositionsJob : IJobParallelFor
{
    public NativeArray<float3> positions;
    [ReadOnly] public NativeArray<float3> velocities;
    public float deltaTime;

    public void Execute(int index)
    {
        positions[index] += velocities[index] * deltaTime;
    }
}

// [BurstCompile]을 추가하는 것만으로 Burst 최적화 적용
// Vector3 대신 float3 (Unity.Mathematics) 사용 권장
// Burst가 SIMD 벡터화, 루프 언롤링 등 자동 최적화 수행
```

<br>

Burst로 컴파일한 Job은 일반 C# 코드보다 크게 빨라질 수 있습니다. 특히 위치 갱신, 거리 계산, 행렬 연산처럼 수학 연산이 많고 데이터 구조가 규칙적인 작업에서 효과가 큽니다. 반면 분기가 많거나 메모리 접근 패턴이 불규칙한 작업에서는 SIMD 벡터화가 어렵기 때문에 효과가 제한될 수 있습니다.

<br>

### Burst의 제약

Burst가 모든 C# 코드를 받아들이는 것은 아닙니다. Burst가 다루는 범위는 **HPC#(High-Performance C#)**, 곧 C#의 부분 집합으로 한정됩니다.
그래서 관리 객체(class 인스턴스)나 문자열, try-catch, virtual 메서드 호출, 그리고 가비지 컬렉션이 필요한 코드는 쓸 수 없습니다. 대신 값 타입(struct)과 NativeContainer, Unity.Mathematics의 타입은 그대로 사용할 수 있습니다.

<br>

| 사용 가능 | 사용 불가 |
|----------|----------|
| `struct` | `class` |
| `NativeArray<T>` | `List<T>`, `Dictionary<K,V>` |
| `float`, `int`, `bool` | `string` |
| `float3`, `float4x4` | 박싱 |
| `math.sin()`, `math.dot()` | `try-catch` |
| `if`, `for`, `while` | `virtual` 메서드 |
| 함수 호출 (인라인 가능) | 인터페이스 디스패치 |
| `NativeArray` 인덱싱 | GC 할당 |

<br>

이런 제약은 불편해 보이지만, Burst가 빠른 코드를 만들기 위한 전제 조건에 가깝습니다. 관리 객체와 GC를 제외하면 두 가지 이점이 생깁니다.

먼저 NativeContainer처럼 연속된 메모리에 놓인 데이터를 다루기 쉬워져 CPU 캐시 효율이 좋아집니다. 또한 런타임에 GC가 메모리를 이동하거나, 가상 디스패치로 호출 대상이 달라지는 경우가 줄어듭니다. 그만큼 컴파일러가 메모리 접근과 실행 순서를 더 쉽게 예측할 수 있습니다.

LLVM은 이 예측 가능성을 바탕으로 SIMD 벡터화와 루프 최적화를 더 적극적으로 적용할 수 있습니다.

<br>

Job System과 Burst 컴파일러는 Unity의 **DOTS(Data-Oriented Technology Stack)** 아키텍처를 구성하는 핵심 요소이기도 합니다. DOTS는 여기에 ECS(Entity Component System, 데이터를 엔티티·컴포넌트·시스템으로 나누어 관리하는 아키텍처)를 더해, 많은 오브젝트를 캐시 친화적인 방식으로 처리하도록 설계된 기술 묶음입니다.

## NativeContainer

NativeContainer는 Job System에서 사용할 수 있도록 설계된 네이티브 메모리 기반 컨테이너입니다. GC가 관리하는 일반 C# 컬렉션 대신 명시적인 수명과 안전성 검사를 가진 자료구조를 사용해 워커 스레드에서 데이터를 안전하게 다룰 수 있게 합니다.

### Job에서 안전한 데이터 공유

대신 GC가 자동으로 정리해 주지 않으므로, 사용이 끝나면 반드시 `Dispose()`를 호출해 직접 해제해야 합니다. 이를 빠뜨리면 메모리 누수로 이어집니다.

<br>

### 할당 수명 (Allocator)

네이티브 메모리는 직접 해제해야 하므로, 생성 시점에 메모리가 얼마나 오래 유지될지를 정해야 합니다. 이 수명을 지정하는 값이 **Allocator**입니다. NativeContainer를 만들 때 어떤 Allocator를 사용하는지에 따라 메모리의 권장 사용 기간과 해제 방식이 달라집니다.

<br>

| Allocator | 용도와 수명 |
|-----------|------------|
| `Allocator.Temp` | 1프레임 이내 사용. 할당/해제 속도 가장 빠름. 프레임 종료 시 자동 해제. 메인 스레드에서 Job으로 전달 불가 |
| `Allocator.TempJob` | Job에 전달 가능. 수동 Dispose 필요. 4프레임 이내에 Dispose하지 않으면 콘솔 누수 경고 출력 |
| `Allocator.Persistent` | 수명 제한 없음. 할당 속도 가장 느림. 수동 Dispose 필수. 여러 프레임에 걸쳐 유지 |

<br>

세 Allocator는 용도가 다릅니다. 한 프레임 안에서만 사용하는 임시 데이터라면 `Allocator.Temp`가 적절합니다. Job에 전달해야 하며 몇 프레임 안에 끝나는 작업이라면 `Allocator.TempJob`을 사용합니다. 경로 맵이나 공간 분할 구조처럼 여러 프레임 또는 씬 전체 동안 유지해야 하는 데이터는 `Allocator.Persistent`로 만들고, 해당 오브젝트가 파괴될 때 직접 `Dispose()`를 호출합니다.

<br>

### 안전성 검사

여러 Job이 같은 NativeContainer에 동시에 쓰기 접근하면 서로의 값을 덮어쓰는 데이터 경합이 생길 수 있습니다. 이를 막기 위해 Job System은 NativeContainer에 누가 어떤 방식으로 접근하는지 스케줄링 시점과 런타임에 검사하는 **안전성 시스템(Safety System)**을 제공합니다.

<br>

```csharp
// Job System의 안전성 검사

[ReadOnly] public NativeArray<float3> positions;

// 이 Job에서 positions에 쓰기를 시도하면 런타임 에러

public NativeArray<float3> results;

// 두 개의 Job이 동시에 같은 NativeArray에
// 쓰기 접근하면 런타임 에러

// 데이터 경합을 Job System이 자동으로 감지
// 기존 멀티스레드 프로그래밍의 락/뮤텍스가 불필요
```

<br>

기본 규칙은 읽기와 쓰기를 구분하는 것입니다. NativeContainer에 `[ReadOnly]` 어트리뷰트를 붙이면 해당 Job에서 쓰기 접근이 막힙니다. 읽기 전용 데이터는 여러 Job이 동시에 읽을 수 있습니다. 반면 쓰기가 필요한 NativeContainer는 같은 시점에 하나의 Job만 접근할 수 있도록 제한됩니다.

이 규칙을 Job System이 강제하므로, 많은 경우 개발자가 락이나 뮤텍스를 직접 작성하지 않아도 됩니다. 다만 안전성 검사는 에디터와 Development Build에서 주로 활성화되며, Release Build에서는 성능을 위해 꺼질 수 있습니다. 따라서 데이터 접근 문제는 개발 단계에서 미리 확인하는 편이 좋습니다.

여기까지는 데이터를 안전하게 나누어 처리하는 방법이었습니다. 하지만 Unity API 자체는 여전히 메인 스레드에서만 호출해야 하는 경우가 많으므로, 다음 절에서는 백그라운드 작업 결과를 메인 스레드로 넘기는 방법을 살펴봅니다.

## Unity API의 메인 스레드 제약과 우회

백그라운드 스레드에서 실행한 코드도 최종적으로 Unity 오브젝트에 결과를 반영해야 할 때가 있습니다. 네트워크 응답을 UI에 표시하거나, 파일 I/O가 끝난 뒤 씬을 갱신하는 작업이 그런 예입니다. Unity API는 대부분 메인 스레드에서만 호출할 수 있으므로, 백그라운드 작업 결과를 메인 스레드로 넘겨 처리하는 패턴이 필요합니다.

<br>

### UnitySynchronizationContext

`await`로 비동기 작업을 기다린 뒤 다음 코드가 어느 스레드에서 이어질지는 SynchronizationContext가 정합니다. 비동기 작업이 끝났을 때 후속 코드를 어느 실행 큐에 올릴지 결정하는 역할을 합니다.

Unity는 시작 시점에 메인 스레드에 `UnitySynchronizationContext`를 설정합니다. 그래서 일반적인 Unity 스크립트에서 `await` 뒤에 이어지는 코드는 백그라운드 작업을 기다린 뒤 다시 메인 스레드에서 실행됩니다. 이 덕분에 `await` 이후에는 Unity API를 호출할 수 있습니다.

> `async/await`과 SynchronizationContext의 동작 원리는 [C# 런타임 기초 (4) - 스레딩과 비동기](/dev/unity/CSharpRuntime-4/)에서 자세히 다룹니다.

<br>

```csharp
// async/await로 메인 스레드 복귀

async void LoadDataAndApply()
{
    // 1. 메인 스레드에서 시작
    string url = _dataUrl;

    // 2. 네트워크 요청을 비동기로 실행 (await로 완료 대기)
    string json = await DownloadAsync(url);

    // 3. await 후에는 메인 스레드로 자동 복귀
    //    (UnitySynchronizationContext 덕분)
    ParseAndApply(json);
    gameObject.SetActive(true);    // Unity API 호출 가능
}

// await 이후에 UnitySynchronizationContext가
// 메인 스레드에서 후속 코드를 실행하도록 스케줄링
```

<br>

위 코드에서 `await DownloadAsync(url)` 다음에 실행되는 `ParseAndApply`와 `SetActive`는 다시 메인 스레드에서 실행됩니다. 따라서 스레드를 직접 전환하는 코드를 작성하지 않아도 됩니다.

> 코드 예시의 `async void`는 호출자가 예외를 관찰하거나 완료를 대기할 수 없으므로, 실무에서는 `async Task`를 반환하는 것이 안전합니다. [C# 런타임 기초 (4)](/dev/unity/CSharpRuntime-4/)에서 `async void`의 문제와 대안을 상세히 다룹니다.

다만 `await`로 기다리는 동안 해당 GameObject가 파괴되거나 씬이 바뀔 수 있습니다. 그러면 이어서 실행되는 코드가 이미 사라진 오브젝트에 접근해 `MissingReferenceException`을 만날 수 있습니다. 코루틴은 MonoBehaviour가 파괴될 때 함께 멈추지만, async 메서드는 자동으로 멈추지 않습니다. 비동기 작업이 끝나면 continuation이 `UnitySynchronizationContext`의 실행 큐에 들어가고, 오브젝트 생존 여부와 관계없이 재개될 수 있기 때문입니다.

그래서 `await` 이후에는 `this == null`로 생존 여부를 확인하거나, 비동기 작업에 `CancellationToken`을 전달하는 편이 안전합니다. Unity 2022.2 이상이라면 MonoBehaviour가 제공하는 `destroyCancellationToken`을 넘겨, 오브젝트가 파괴되는 순간 비동기 작업에 취소 신호가 전달되도록 만들 수 있습니다.

<br>

### 메인 스레드 디스패치 패턴

`UnitySynchronizationContext`의 핵심은 작업을 큐에 넣어 두었다가 메인 스레드에서 실행하는 디스패치입니다. 같은 원리를 async/await에 의존하지 않고 직접 구현할 수도 있습니다.

<br>

```csharp
// 큐 기반 메인 스레드 디스패치

ConcurrentQueue<Action> _mainThreadQueue = new();

// 백그라운드 스레드에서:
void OnNetworkResponse(string data)
{
    _mainThreadQueue.Enqueue(() =>
    {
        // 이 코드는 메인 스레드에서 실행됨
        UpdateUI(data);
        gameObject.SetActive(true);
    });
}

// 메인 스레드에서 (Update):
void Update()
{
    while (_mainThreadQueue.TryDequeue(out Action action))
    {
        action.Invoke();
    }
}

// 백그라운드 스레드: 큐에 작업 추가
// 메인 스레드: Update에서 큐의 작업을 꺼내 실행
// Unity API 호출은 메인 스레드의 Update에서만 발생
```

<br>

여기서 사용한 `ConcurrentQueue<T>`는 스레드 안전한(Thread-Safe) 큐입니다. 백그라운드 스레드는 `Enqueue`로 작업을 추가하고, 메인 스레드는 `Update`에서 `TryDequeue`로 작업을 꺼내 실행합니다. 이 패턴을 사용하면 async/await 없이도 백그라운드 작업 결과를 메인 스레드로 전달하고, Unity API를 메인 스레드에서만 호출하는 규칙을 지킬 수 있습니다.

<br>

### Job System vs 직접 스레딩

Job System과 직접 스레딩은 목적이 다릅니다. Job System은 데이터를 병렬로 계산하는 작업에 적합하고, 직접 스레딩이나 async/await는 I/O 대기가 긴 비동기 작업에 적합합니다.

| 항목 | Job System | 직접 스레딩 (System.Threading, async/await) |
|------|-----------|-----------------|
| 안전성 검사 | 자동 (스케줄링/런타임) | 수동 (개발자 책임) |
| 데이터 경합 방지 | NativeContainer로 자동 보장 | 락/뮤텍스 직접 관리 |
| Burst 사용 | 가능 | 불가 |
| Unity API 호출 | 불가 (Job 내부) | 불가 (백그라운드 스레드) |
| 데이터 전달 | NativeContainer | 공유 변수, 큐 등 |
| 적합한 용도 | 데이터 병렬 연산 (수학, 위치 갱신) | I/O, 네트워크 등 대기가 긴 작업 |

<br>

적의 위치 갱신, 경로 탐색, 시야 검사처럼 많은 데이터를 병렬로 계산하는 작업이라면 Job System이 적합합니다. 여기에 Burst 컴파일을 적용하면 계산 성능을 더 높일 수 있습니다. 반면 네트워크 통신이나 파일 I/O처럼 결과를 기다리는 시간이 긴 작업에는 `async/await`나 `System.Threading`이 더 잘 맞습니다.

비동기 처리에는 표준 `Task` 기반 async/await 외에도 선택지가 있습니다. Unity 2023.1 이상의 `Awaitable`은 PlayerLoop와 직접 연결되어 `SynchronizationContext` 캡처 없이 메인 스레드에서 재개될 수 있고, 내부 풀링으로 힙 할당을 줄입니다. 서드파티 라이브러리인 UniTask도 힙 할당을 줄인 async/await 실행과 PlayerLoop 재개 시점 제어를 제공합니다.

> 이들 비동기 기법의 상세한 비교는 [C# 런타임 기초 (4) - 스레딩과 비동기](/dev/unity/CSharpRuntime-4/)에서 다룹니다.

## 마무리

Unity의 스레딩 모델은 메인 스레드를 중심으로 구성됩니다. `MonoBehaviour` 콜백과 Unity API 호출은 메인 스레드에서 처리되고, 렌더 스레드는 GPU 명령 제출을 담당하며, Job System은 계산 작업을 워커 스레드로 나누어 실행합니다. 핵심은 다음과 같습니다.

- **메인 스레드**는 `MonoBehaviour` 콜백, 애니메이션, 물리 시뮬레이션 시작, 렌더링 준비를 담당합니다. Unity API 대부분은 메인 스레드에서만 호출할 수 있습니다.
- **렌더 스레드**는 메인 스레드가 준비한 렌더링 명령을 GPU에 제출합니다. 두 스레드는 서로 다른 프레임의 작업을 병렬로 처리할 수 있습니다.
- **동기화 마커**는 병목을 판단하는 단서입니다. `Gfx.WaitForPresentOnGfxThread`는 GPU 병목이나 VSync 대기를, `Gfx.WaitForCommands`는 메인 스레드 병목을 의심할 때 확인합니다.
- **Job System**은 `IJob`, `IJobParallelFor`, `JobHandle`을 통해 작업을 워커 스레드에서 실행하고 의존성을 관리합니다.
- **Burst 컴파일러**는 Job 코드를 LLVM 기반 네이티브 코드로 바꾸고 SIMD 자동 벡터화를 적용해 수학 연산이 많은 작업의 실행 속도를 높입니다.
- **NativeContainer**는 Job에서 사용할 수 있는 네이티브 메모리 기반 데이터 구조입니다. GC 부담은 줄어들지만 사용 후 `Dispose()`로 직접 해제해야 합니다.
- **메인 스레드 복귀**는 백그라운드 작업 결과를 Unity API에 반영할 때 필요합니다. async/await의 `UnitySynchronizationContext`나 큐 기반 디스패치 패턴을 사용해 결과 처리를 메인 스레드로 넘길 수 있습니다.

스레딩 모델을 끝으로 Unity 엔진 핵심 시리즈는 마무리됩니다. GameObject와 Component 구조에서 시작해 Transform 계층, 실행 순서, 스레딩 모델까지 살펴보면 Unity가 어떤 구조로 프레임을 처리하는지 큰 흐름을 잡을 수 있습니다. 특히 어떤 코드가 어느 스레드에서 실행되는지 알면, 프레임이 느려졌을 때 Profiler에서 확인해야 할 위치가 분명해집니다.

이 기초 위에서 [게임 루프의 원리 (2) - CPU-bound와 GPU-bound](/dev/unity/GameLoop-2/)에서는 병목을 구분하는 방법을, [스크립트 최적화](/dev/unity/ScriptOptimization-1/) 시리즈에서는 스크립트 비용을 줄이는 방법을, [C# 런타임 기초 (4) - 스레딩과 비동기](/dev/unity/CSharpRuntime-4/)에서는 스레드 관리와 비동기 패턴을 더 자세히 다룹니다.
